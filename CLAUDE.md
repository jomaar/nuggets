## Rules
- No raw SQL — Prisma only
- Colors via CSS vars (globals.css), not Tailwind colors
- Tags: stored as JSON string → always `JSON.parse(n.tags)`
- Content: always sanitized via lib/content.ts. Canonical format = `contentHtml` (Tiptap, may contain highlight `<mark data-color>` AND coloured underline `<u data-color>`). `contentMarkdown` is a DERIVED projection for the AI (via `htmlToMarkdown`, strips `<mark>` and `<u>`); `contentPlain` for search. Editor: `components/NuggetEditor.tsx` (Tiptap). Highlights roadmap: PLAN.md Phase 6.
- Markings (two styles, one system): highlights = `CssVarHighlight` (`<mark data-color>`, 6 pastel colours) and thick coloured underlines = `CssVarUnderline` (`<u data-color>`, 6 SEPARATE saturated colours — pastel is unreadable as a line). Both palettes live in `lib/marking.ts` (single source of truth; CSS vars `--hl-*` / `--ul-*` + `mark[data-color]` / `u[data-color]` rules in globals.css — underline styling via `text-decoration-thickness: 0.2em`, NOT border-bottom). `CssVarUnderline` extends the stock Underline mark (StarterKit's bundled copy is DISABLED via `underline: false` — re-enabling it duplicates the mark); plain `<u>` without `data-color` (imported HTML) round-trips untouched. The BubbleMenu has two swatch rows (hl / ul); ✕ removes BOTH mark types from the selection. The single-view marks popup + scroll/deeplink all use the shared `MARK_SELECTOR` (`'mark, u[data-color]'`) — its querySelectorAll index is the popup's `markIndex`, so every consumer must use that exact selector. Overlap hl+ul on the same text is allowed (nested in HTML → popup lists the two markings as separate rows).
- Named colours per nugget (Etappe 2): each (style, colour) can carry a nugget-specific meaning. Stored as `Nugget.markScheme` (JSON string, `tags` pattern; sparse — only named entries, keys `"hl:yellow"`/`"ul:red"`). All types/helpers in `lib/marking.ts`: `MarkScheme`, `markKey`, `markLabel` (custom name → fallback default label), `hasMarkLabel`, `parseMarkScheme` (tolerant), `sanitizeMarkScheme` (API validation: known keys only, non-empty trimmed strings, `MARK_LABEL_MAX` 60 — PATCH 400s on non-object, silently drops bad entries). GET `/api/nuggets/:id` + list GET ship `markScheme`; `/api/due` includes it implicitly. UI: BubbleMenu swatches show the name as a mini label under the swatch (`.swatch-cell`/`.swatch-label` in globals.css, label max-width = swatch width so 6 cells fit narrow iPhones; when a row has ≥1 name, EVERY cell in that row gets a label slot — ` ` blank — so swatches stay on one baseline). `NuggetEditor` takes prop `markScheme` (parsed object), passed from single view (`NuggetReader`), `NuggetCard`, and `app/edit`. **Legende** = section at the top of the single-view marks popup: one row per (style, colour) that occurs in the document OR is named; owner gets an uncontrolled input (commit on blur/Enter → `commitMarkLabel` PATCHes `{ markScheme }` — metadata only, never touches `contentHtml`, so it can't collide with the debounced highlight save). Named marks also show their name above the popup row text. Editing names lives ONLY in the single view; edit view swatches display them read-only.
- Markierungen ein-/ausblenden (2026-07-06, concept from `../markingtool`): eye buttons in the marks-popup legend — one per row + a master eye in the legend header (all at once) — switch a (style, colour) pair's STYLING off in the reading view (plain text; contentHtml/DOM untouched, so `MARK_SELECTOR` indices, jump + deeplinks keep working; hidden legend/popup rows dim to 0.45). Mechanism: the single view puts `mark-hidden-<kind>-<colour>` classes on the content wrapper (same wrapper as `verses-hidden`); the neutralising rules live in globals.css and route through `.nugget-content` to out-specify the base mark/u rules — hiding `hl:yellow` also covers `mark:not([data-color])` (defaults to yellow). Viewing preference for ANY reader (not owner-gated), per nugget in sessionStorage (`nugget-hidden-marks-<id>`); edit view + print route never get the classes. **„Nur Text"-Master (2026-07-14)**: first button in the sticky-bar view row — one tap to read the document completely unannotated (verse markers + ALL marking styles + comment indicators off at once). Pure OVERRIDE: state `pureText` (sessionStorage `nugget-pure-<id>`) forces `verses-hidden` + the blanket class `marks-hidden-all` (globals.css; bare `mark` selector covers `mark:not([data-color])`) on the wrapper and skips painting the annotation layer — the three individual settings keep their stored values, so switching back restores the exact fine-grained state. While on, the individual toggles (Versangaben ×2, Kommentarstellen, legend eyes incl. master eye) are `disabled` + dimmed; the invisible comment tap targets are dead like in the existing hidden mode (sheet opens via toolbar only).
- **Semantische Dimensionen (2026-08-06)** — the rule that makes markings comparable across the whole corpus: **COLOUR carries the dimension, STYLE carries the level.** Highlights mark STATEMENTS (what the text claims), underlines mark LANGUAGE (how the text works), so a colour's hl and ul are the same idea one level apart. Derived from a corpus analysis of the real `faith` domain (45 nuggets, 194 merged marks): the average span length separates the styles cleanly (ul 2.8–5.6 words = connectors/imperatives/lexemes, hl 7.4–14.9 words = theses/poles/own thoughts). The six: 🟡 Gelb **Kern** (zentrale Aussage / zentrales Wort) · 🟠 Orange **Grund** (worauf es sich stützt / Verweisformel) · 🩷 Pink **Gegen** (was abgewehrt wird / Negation im Wortlaut) · 🟢 Grün **Folge** (was gilt / Imperativ — der Indikativ-Imperativ-Zusammenhang) · 🔵 Blau **Aufbau** (Denkbewegung / Konnektor) · 🟣 Lila **Ich** (mein Gedanke / meine offene Frage). Merksatz: *worum es geht · woher es kommt · wogegen es steht · was folgt · wie es gebaut ist · was ich denke.* `MARK_DIMENSIONS` + `markDimension(color)` + `markGloss(kind,color)` in `lib/marking.ts`. **The dimension depends ONLY on the colour, never on the applied template** — that is what makes it a TOTAL function over every mark and lets Denkspuren bucket by it with zero configuration. Palette display order was resorted to match the spectrum: `Gelb · Orange · Pink · Grün · Blau · Lila` (warm→cool, the opposing pair Pink/Grün adjacent); only the array order in `HIGHLIGHT_PALETTE`/`UNDERLINE_PALETTE` changed — `name` stays the stored `data-color`, so there was NOTHING to migrate, and the index-pairing of the two palettes (which `legendRows` relies on) still holds. 6 colours is a hard ceiling, not a preference: `.swatch-label` width is what caps the BubbleMenu row (see the sum in globals.css), and the corpus analysis found exactly 12 real functions for the 12 slots.
- **Markierungs-Vorlagen (`MarkTemplate`, 2026-08-06)**: a reusable naming scheme for the 12 slots, specializing the LABELS inside the fixed dimension frame per text genre. Three seeded `builtIn` templates (`prisma/seed.ts`, upsert on `name`, `update: {}` so owner edits survive a redeploy): **Exegese** (Sekundärtext/Analyse — der Standardfall), **Position** (Debatte/Sekundärliteratur), **Bibeltext** (Primärtext). Bibeltext differs from Exegese in only two slots (`Gegen`→`Warnung`, `Gilt`→`Zusage`) — deliberate, so muscle memory transfers. Model = `name` unique + `scheme`/`glossary` as JSON strings (`tags` pattern, both validated by `sanitizeMarkScheme`) + `builtIn` + `sortOrder`; `Nugget.markTemplateId` FK with **`onDelete: SetNull`**. **Applying a template COPIES `scheme` into `Nugget.markScheme`** — so no rendering path ever resolves a template; `markTemplateId` exists purely so the popup can show the name and the long-form glossary. Labels are capped at **7 characters** by design (swatch-label width); the long text lives in `glossary`. API: `GET /api/mark-templates` (public) + `POST` (owner, „Als Vorlage speichern", 409 on duplicate name) + `PATCH`/`DELETE /api/mark-templates/[id]` (owner; DELETE 400s on `builtIn` — the seed would recreate it anyway). `markTemplateId` accepted by `PATCH /api/nuggets/:id` and shipped by its GET. Helpers in `lib/markTemplates.ts` (`MarkTemplateView`, `listMarkTemplates`, `toTemplateView` — tolerant JSON parsing, one bad row can't kill the list). UI in the marks-popup legend header: a **pill naming the active template** („Keine Vorlage" when hand-made), a **`BookOpen` glossary toggle** (any reader — it is a reading aid) that expands every legend row with `Dimension · Langtext` (template wording wins, `markGloss` fallback so the panel is never empty), and a **`Save` button** for „Als Vorlage speichern". ⚠️ **The template picker is the EXISTING import dialog extended**, not a new one — templates render as a „Vorlagen" section above „Andere Nuggets", both through `SchemeSourceCard` and the same `pickImportSource`/`applyImport` path, so the Ersetzen/Ergänzen question comes for free. **Ergänzen is the important branch**: `{ ...source, ...local }` keeps nugget-specific meanings like „Leiden-Bedrängnis-Schmach-Tod" alive when a template lands (verified end-to-end).
- Scheme import (Etappe 3): „Übernehmen von …" button in the legend header (owner-only; the legend section renders even with zero rows so import works on unmarked nuggets) → dialog listing every OTHER nugget with a non-empty `markScheme` (client-filtered from the list GET; title + swatch/name preview). No local names → plain copy, no question; otherwise ask **Ersetzen** (source 1:1) vs. **Ergänzen** (`{ ...source, ...local }` — local names win, source only fills gaps). Apply = `PATCH { markScheme }`, metadata copy only. The legend inputs are uncontrolled, so their `key` includes the scheme VALUE — an import/rename must remount them or they'd show stale names.
